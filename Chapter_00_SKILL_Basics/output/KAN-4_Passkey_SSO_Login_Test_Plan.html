1. Scope & Objectives

In scope

  • UI visibility & placement (AC1): presence and position of the “Sign in using SSO” and “Sign in with Passkey” options on the login page, including their placement below the “Sign in with Google” option.
  • SSO login flow (AC2): happy path (valid SSO credentials → authenticated → dashboard) and negative path (invalid credentials → appropriate error message).
  • Passkey login flow (AC3): happy path (registered & verified passkey → logged in → dashboard), and the “no passkey available” fallback / guidance path.
  • Error handling (AC4): failed SSO authentication, passkey authentication failure, and unsupported browser/device for passkeys.
  • Compatibility (AC5): passkey flow across supported browsers/devices; SSO across all configured identity providers.
  • Security (AC6): secure protocols (OAuth / SAML / WebAuthn) and no exposure of sensitive data in the UI or network logs.
  • Regression of existing auth: email/password and “Sign in with Google” must remain unaffected.

Out of scope (per ticket)

  • Passkey registration flow — covered in a separate story.
  • SSO provider configuration / IdP setup.
  • Redesign of existing authentication methods beyond verifying no regression.

Objective

“Tested” for this ticket means every acceptance criterion is demonstrated as an observable pass/fail; both new login flows are verified secure, reliable and usable across supported environments; the three defined error states behave correctly and leak no sensitive data; and existing login methods continue to work without regression.

Tech / platform context

WebAuthn (Passkey) OAuth / SAML (SSO) Web login page Redirect to Dashboard

Note: Protocol details (SAML vs OAuth per IdP, which WebAuthn platform authenticators are supported) are not stated in the ticket and are flagged in Section 2 as gaps.
